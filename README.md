# FrameBench: A Semantic Understanding Benchmark Based on Frame Semantics

<p align="center">
This repository contains the code for building a frame-knowledge-based semantic understanding benchmark for LLMs and for evaluating LLMs on it.

> [!NOTE]
> The FrameNet-derived frame knowledge used to build the benchmark is not distributed in this repository.
> Evaluation on the released benchmarks is supported for both Japanese and English.

## 📋 Overview
This project consists of the following steps:

- Building the benchmark
  - Step 1: Preprocessing frame knowledge
  - Step 2: Generating QA items
  - Step 3: Generating additional sentences
- Running the evaluation

## 🚀 Setup

### 1. **Install uv**
```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
export PATH="$HOME/.local/bin:$PATH"
```

### 2. **Install dependencies**

**If you only run the evaluation:**
```bash
uv sync

# To also evaluate local models with vLLM
uv sync --extra vllm
```

**If you also run benchmark generation:**
```bash
uv sync --extra generation
```
To install all packages at once, run `uv sync --extra all`.

### 3. **Set environment variables**
Create a `.env` file in the project root according to the APIs you use.

```bash
cat << EOF > .env
OPENAI_API_KEY=your_api_key_here
GOOGLE_API_KEY=your_api_key_here
ANTHROPIC_API_KEY=your_api_key_here
EOF
```

You can omit lines for APIs you do not use. No API key is required when evaluating local models with vLLM.

## 🛠️ Building the benchmark
See [`src/generation/config.yaml`](src/generation/config.yaml) for the available generation models.
By default, the scripts below process Japanese (`LANGUAGE=ja`). To use another language,
prepare the corresponding FrameNet data and generation prompts, then specify `LANGUAGE` and `PROMPT_FILE`.

### Step 1: Preprocessing frame knowledge

Converts FrameNet XML into JSONL format. Place the XML files, named after their evoking words,
under `data/<language>-framenet/raw_frame/`.

```bash
# Japanese (default)
bash scripts/step1.sh

# Change the language or data root
LANGUAGE=en DATA_ROOT=data bash scripts/step1.sh
```

**Output:**
- Parsed frame data: `data/<language>-framenet/frames.jsonl`
- Parsed lexical unit data: `data/<language>-framenet/lexical_units.jsonl`

In addition to these, Step 2 uses `data/<language>-framenet/exemplars.jsonl` as input.
This file is not generated by Step 1, so please prepare it separately.

### Step 2: Generating QA items

Generates sentence pairs and question texts from FrameNet exemplar sentences. If the model is omitted, `gpt-4.1-mini` is used.

```bash
# Check with a small number of items (defaults: NUM=10, NUM_PAIRS=2)
bash scripts/step2.sh gpt-4.1-mini

# Generate all items
NUM= bash scripts/step2.sh gpt-4.1-mini

# Specify language, number of items, and prompt
LANGUAGE=en NUM=100 PROMPT_FILE=path/to/make_qa_en.toml \
  bash scripts/step2.sh gemini-3.1-pro-preview
```

**Output:**
- QA items (including sentence pairs): `data/<language>/<model>/step2/qa.jsonl`
- Intermediate results, input logs, and API responses: in the same `step2/` directory

**Optional: Manual text correction (Step 2)**

To improve the quality of the generated QA items, you can correct the text manually. See [`tools/README.md`](tools/README.md) for details.

After annotation, you can merge the annotation results with the following command:

```bash
cd tools
uv run python postprocess/for_step2.py --input_file data/<language>/<model>/step2/qa.jsonl
```

The corrected QA data is saved to `data/<language>/<model>/step2+annotation/text_corrected_qa.jsonl`.

### Step 3: Generating additional sentences

Generates additional sentence pairs for each Step 2 item to ensure diversity of the questions.

```bash
# Check with a small number of items (default: MAX_ITEMS=5)
bash scripts/step3.sh gpt-4.1-mini

# Generate all items
MAX_ITEMS= bash scripts/step3.sh gpt-4.1-mini

# Use the manually corrected QA data as input
QA_FILE=data/ja/gpt-4.1-mini/step2+annotation/text_corrected_qa.jsonl \
  bash scripts/step3.sh gpt-4.1-mini
```

**Input:**
- Default: `data/<language>/<model>/step2/qa.jsonl`
- Any QA file can be specified with `QA_FILE`

**Output:**
- QA data with a four-sentence structure: `data/<language>/<model>/step3/qa.jsonl`
- Per-batch input logs and API responses: in the same `step3/` directory

**Optional: Manual annotation (Step 3)**

The Step 3 data can also be evaluated manually. See [`tools/README.md`](tools/README.md) for details.

After annotation, you can merge the annotation results with the following command:

```bash
cd tools
uv run python postprocess/merge_eval_rounds.py --base_dir data/ja/gpt-4.1-mini/step3
```

The merged QA data is saved to `data/<language>/<model>/step3/qa_annotated.jsonl`.

## 🛠️ Evaluation

FrameBench evaluates LLMs with four-choice questions. Since evaluation results vary with the prompt,
we recommend evaluating with the five bundled prompts and using the average.

Per-model settings such as backend, thinking, sampling, and structured outputs are managed in
[`src/evaluation/model_profiles.yaml`](src/evaluation/model_profiles.yaml).
Registered models automatically use either an OpenAI-compatible API or vLLM according to their profile.

### Adding a model

You can evaluate any model by adding a profile under `models` in `model_profiles.yaml`.
For example, if you register `gpt-5`, the same settings are also used for versioned model names
starting with `gpt-5`, such as `gpt-5-2026-08-01`. If an exactly matching entry exists, it takes precedence.

```yaml
models:
  organization/thinking-model:
    backend: vllm
    supports_thinking: true
    thinking_stop: "</think>\n\n"
    thinking_sampling:
      temperature: 0.6
      top_p: 0.95
      top_k: 20
    answer_sampling:
      temperature: 0.0
      top_p: 1.0
      top_k: -1
    trust_remote_code: true
```

`supports_thinking: true` indicates that the model supports thinking. It does not enable thinking
automatically; normally you pass `--enable_thinking` at runtime. For models that support
`reasoning_effort`, thinking is also enabled when you pass, for example, `--reasoning_effort medium`.

The main fields are as follows:

- `backend`: `openai` or `vllm`
- `supports_thinking`: whether thinking generation is supported
- `reasoning_effort`: supported reasoning levels (e.g. `[low, medium, high]`)
- `thinking_stop`: the string that ends the thinking phase
- `sampling`: sampling settings for the no-thinking mode
- `thinking_sampling`: sampling settings for the thinking phase
- `answer_sampling`: sampling settings for the answer phase after thinking
- `thinking_generation_mode`: generation method when thinking. The default `two_phase` generates the thoughts without constraints and then constrains the answer to `1/2/3/4`, while `single_json` outputs everything from the thoughts to `{"answer":"N"}` in a single generation
- `skip_special_tokens`: whether to strip special tokens during vLLM decoding
- `no_thinking_generation_prefill`: a string prepended at the start of generation only in the no-thinking mode
- `trust_remote_code`: whether to allow custom code for Hugging Face models
- `supports_multimodal`: whether inputs such as images are supported
- `chat_template`: an override for when the tokenizer lacks an appropriate chat template

For OpenAI-compatible APIs, you can also set `base_url`, `api_key_env`, and
`structured_outputs` as needed.

A different profile file can be specified with `--model_profile_file path/to/profiles.yaml`.

> [!CAUTION]
> When evaluating models that emit control tokens before the answer body, such as the Harmony format,
> in the no-thinking mode, this can conflict with the structured-output constraint applied right at the
> start of generation. Check the chat template and the output for a few items, and set
> `no_thinking_generation_prefill` only for the models that need it.
> When thinking, the thinking phase is normally generated without constraints before the answer constraint is applied.

### How to run the evaluation

The convenience script takes the form `MODEL [ja|en] [API_CONCURRENCY] [extra options...]`.
This script enables `--swap_statements`, which also evaluates items with statements A/B swapped,
and sets the tensor parallel size to 4.

```bash
# OpenAI API, Japanese
bash scripts/run_eval.sh gpt-5-nano

# OpenAI API, English, API concurrency 20
bash scripts/run_eval.sh gpt-5-nano en 20

# vLLM with thinking enabled (override TP for a single GPU)
bash scripts/run_eval.sh Qwen/Qwen3-4B ja 10 \
  --enable_thinking --tensor_parallel_size 1
```

Running Python directly lets you specify each condition individually.

```bash
uv run python src/evaluation/eval_multi_prompts.py \
  --model gpt-5-nano \
  --language ja \
  --num 100 \
  --swap_statements \
  --prompt_files eval_prompt/ja/prompt_v1.txt
```

**Main options:**
- `--model`: the LLM to evaluate
- `--language`: `ja` or `en` (default: `ja`)
- `--dataset`: an HF dataset name or a local JSONL file. If unspecified, `cl-nagoya/jFrameBench` is used for Japanese and `cl-nagoya/FrameBench` for English
- `--dataset_split`: the split of the Hugging Face dataset (default: `train`)
- `--num`: the number of four-choice questions to evaluate after expansion (all questions if unspecified)
- `--prompt_files`: the prompt files to use (multiple values allowed; if unspecified, all files under `eval_prompt/<language>/` are used)
- `--output_dir`: the base path of the output directory (default: `output`)
- `--swap_statements`: add mirrored items with statements A/B swapped
- `--reasoning_effort`: the reasoning depth for supported models
- `--no_quality_filter`: disable the quality filter based on manual annotation

**vLLM-specific options:**
- `--enable_thinking`: enable the thinking mode
- `--tensor_parallel_size`: tensor parallel size (default: 1)
- `--gpu_memory_utilization`: GPU memory utilization (default: 0.9)
- `--max_model_len`: maximum model length
- `--max_num_seqs`: maximum number of sequences processed concurrently (vLLM default if unspecified)
- `--max_tokens`: maximum number of generated tokens in the no-thinking mode
- `--thinking_max_tokens`: maximum number of generated tokens in the thinking phase
- `--answer_max_tokens`: maximum number of generated tokens in the answer phase after thinking

The quality filter is enabled by default. Only items for which at least 2 of 3 annotators affirmed both
gold-answer agreement and quality are included in the aggregation, and `summary.txt` and the aggregated
files record the accuracy after filtering. The details for all items remain in `result.tsv`.

**Output:**

```text
output/<language>/<num_or_all>/<model><suffix>/
├── run_config.json
├── aggregated_summary.txt
├── aggregated_summary.tsv
└── <prompt_name>/
    ├── result.tsv
    ├── summary.txt
    └── params.json          # OpenAI-compatible API only
```

`<suffix>` reflects the actual evaluation conditions, such as `_thinking`/`_no_thinking` for vLLM
or `_reasoning_medium` for API models.
